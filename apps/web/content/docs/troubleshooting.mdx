## When to use it

Come here with a symptom or a console message. **Every message the SDK prints is quoted word for word**, so pasting the exact text into this page's search finds it.

Most of what goes wrong here is a setup detail, not a mistake you should feel bad about — several of the worst cases produce no error at all, which is exactly why they cost hours. If something looks broken, check this page before you start deleting `node_modules`.

If you are setting up for the first time and nothing has gone wrong yet, [Quick start](/docs/getting-started/quick-start) ends with a "Verify it works" checklist that catches most setup problems before they become symptoms.

## Basic usage

The three checks that resolve most issues:

```bash title="1. Is the stylesheet imported?"
# Should appear exactly once, at your app root
grep -r "@cookieyes/react/styles.css" src/ app/
```

```js title="2. What state is the visitor actually in?"
// DevTools console
document.cookie.split("; ").find((c) => c.startsWith("cookieyes-consent="));
```

```js title="3. Reset to a clean slate"
document.cookie = "cookieyes-consent=; max-age=0; path=/";
location.reload();
```

## It looks wrong, and there is no error

The expensive category. Nothing throws, nothing appears in the console, and there is no text to search for — so these are findable here by what you *see* instead.

### The banner appears but has no styling

**What you see.** Everything works — the banner shows, buttons respond, consent saves correctly — but it renders as unstyled text with no card, no colours, no layout.

**Why.** The stylesheet was never imported. Styling ships as a separate file rather than being injected by JavaScript, which is what keeps the SDK compatible with a strict Content-Security-Policy. Nothing warns you, because from the SDK's point of view everything is working.

**Fix.** Import it once, at your app root:

```ts title="app/layout.tsx"
import "@cookieyes/react/styles.css";
```

If the **banner** looks right and only the **preferences dialog** is unstyled, you loaded `critical.css` — the small paint-critical subset — and not the full sheet. Load both; `critical.css` does not replace `styles.css`.

### The banner never appears

**What you see.** No banner, no error, nothing in the console.

**Why.** Three common causes, in the order worth checking:

1. **The visitor already decided.** The banner shows until someone acts, then never again. This is the most common one, and it is correct behaviour — see [Reset and re-test](#reset-and-re-test).
2. **`initCookieYes()` never ran**, or ran in a module that is not `"use client"`. Nothing renders and nothing errors, because the hooks return safe defaults rather than throwing.
3. **The regulation does not apply to you.** With region detection on, the banner may simply not apply where you are testing from.

**Fix.** Clear the cookie and reload; confirm your `initCookieYes()` module starts with `"use client"` and is actually imported on the path to your components; check `useRegion()` for which regulation resolved and why.

### Clicking "Do Not Sell" does nothing

**What you see.** Under CCPA the banner shows a "Do Not Sell" button. Clicking it does nothing at all — no dialog, no error.

**Why.** `Banner.DoNotSell` only *sets state*: it asks for the opt-out dialog to open. If `<CookieOptOut />` — or your own `OptOut.Root` — is not mounted, there is nothing to open.

**Fix.** Mount it alongside the banner:

```tsx title="app/cookieyes.tsx"
"use client";

import { CookieBanner, CookieOptOut, CookiePreferences } from "@cookieyes/react";

export function CookieYesRoot() {
  return (
    <>
      <CookieBanner />
      <CookiePreferences />
      {/* Without this, the banner's "Do Not Sell" button has nothing to open. */}
      <CookieOptOut />
    </>
  );
}
```

The same applies to `showPreferences()` with no `<CookiePreferences />` mounted.

### I withdrew consent and the tracking carried on

**What you see.** A visitor revokes consent for a category, and a tool gated on it keeps running.

**Why.** Injecting a third-party script is one-way within a page load. Once a vendor's code is executing, the SDK can ask it to stop — and does, where the vendor supports it — but it cannot un-run what already ran. Some tools have no clean stop at all and genuinely need a page reload.

<Callout type="warn">
  **This one has a compliance consequence, not just a cosmetic one.** A visitor who withdraws consent and keeps being tracked for the rest of their session is a real problem, whatever the technical explanation. If you gate anything that cannot stop cleanly, mount [`<ReloadNotice />`](/docs/components/reload-notice) so the visitor is told a reload is needed — or set `reloadOnRevoke: true` to reload for them.
</Callout>

**Fix.** Mount `<ReloadNotice />`. Note it appears only when something that *was* running has been switched off — see [Working as intended](#the-reload-notice-never-appears).

### Someone flicked a switch without saving and it counted

**What you see.** A visitor opens preferences, toggles a category on to read its description, closes without saving — and your tracker loaded anyway.

**Why.** You gated on the **live** values (`useConsent().categories`), which reflect in-progress toggles, rather than the **committed** values, which only change on a real decision.

**Fix.** Gate on [`useConsentCategory(id)`](/docs/hooks/focused-hooks), or on `useConsent().committedCategories`. See [`categories` vs `committedCategories`](/docs/hooks/use-consent#categories-vs-committedcategories) — this is the single most consequential distinction in the API.

### My custom categories did not appear

**What you see.** You configured `categories`, and the built-in five render instead.

**Why.** The config failed validation and the SDK fell back rather than throwing. It **does** warn — this is one of the no-error cases only if you were not watching the console.

**Fix.** Check the console for `[cookieyes] Invalid categories config (...)`. The reason is in the parentheses: every category needs a non-empty string `id`, ids cannot contain `,` or `:`, ids must be unique, ids must not collide with the reserved cookie keys, and **at least one category must be marked `required: true`**.

### My banner is in English even though I set another language

**What you see.** `locale` or `setLanguage("fr")` is set, and the interface stays English.

**Why.** Setting a language does not supply the words for it. If there is no catalogue for that tag in `i18n.messages` and no `i18n.loadLanguage` to fetch one, the SDK stays on the language it has.

**Fix.** Add the catalogue. The console warns once per language tag: `[cookieyes] no translations for language "..."`.

### My floating button lost all its styling

**What you see.** You passed a `className` to `<RecallButton />` and it lost its appearance entirely.

**Why.** `RecallButton` **replaces** its class rather than merging: your class is used *instead of* `cy-widget`, not alongside it. This differs from the headless primitives, which merge your class with theirs — so the behaviour is genuinely inconsistent between the two, and nothing warns.

**Fix.** Include the base class yourself:

```tsx title="Keep the base styling"
<RecallButton className="cy-widget my-custom-class" />
```

### The visitor's choice isn't remembered

**What you see.** Consent is recorded, then forgotten on the next page load.

**Why.** The decision lives in a first-party cookie named `cookieyes-consent`. It goes missing for three ordinary reasons: browser privacy settings or an extension blocking storage, a strict cookie policy on your own domain, or — most often — your own code clearing cookies on navigation or on every deploy.

**Fix.** Confirm the cookie survives a reload in DevTools. If it does not, check what else on your site writes to `document.cookie`.

## Errors

### `[cookieyes] No runtime is registered.`

**This almost never actually shows up.** A missing `initCookieYes()` or a missing `"use client"` does not throw — every hook and every styled component reads the runtime through a non-throwing accessor and degrades silently instead: no banner, nothing in the console, hooks returning their safe defaults, actions doing nothing. That silence is the real symptom, and it is harder to diagnose precisely because there is no error to search for. Check, in order of likelihood:

1. The config lives in a module nothing imports on the path to your components. A module nobody imports never runs.
2. `initCookieYes()` is in a Server Component — it must be in a `"use client"` module.
3. It is inside a component body rather than at module scope.
4. The components rendering (`CookieBanner`, `CookiePreferences`, ...) are not themselves in a `"use client"` file.

The rule, with a correct and incorrect example side by side, is on [Configuration](/docs/getting-started/configuration#the-rule-that-breaks-most-first-setups).

You will see an actual thrown error only when code calls [`useConsentRuntime()`](/docs/hooks/low-level-hooks) or `getCookieYes()` directly — both skip the safe-default behaviour on purpose, because that low-level escape hatch is meant for code that genuinely requires a runtime to exist:

```text title="Error output"
Error: [cookieyes] No runtime is registered. Call initCookieYes(...) in a 'use client' module before using hooks or components.
```

### `[cookieyes] OptOut.* sub-components must be rendered inside <OptOut.Root>.`

A primitive slot escaped its namespace root — usually after extracting a sub-tree into a component rendered elsewhere. Thrown by the four slots that read the dialog's saved state: `OptOut.Checkbox`, `OptOut.Save`, `OptOut.Buttons` and `OptOut.Success`.

The matching `[cookieyes] Preferences.* sub-components must be rendered inside <Preferences.Root>.` exists in our source but is **not currently wired to any slot**, so it does not fire today. If you have a `Preferences.*` slot outside its root the symptom is silent instead: it renders, and toggling or saving does nothing. Every `Preferences.*` must still be a DOM descendant of `Preferences.Root`.

### `` [cookieyes] `asChild` expects exactly one React element child. ``

You passed text, a fragment, or multiple children to a slot using `asChild`. Wrap in exactly one element.

### `createCookieYes(): .mode() is required before .mount().`

Builder-only. Migrate to `initCookieYes`, where `mode` is a required field the type system enforces. See [Migration](/docs/migration).

### `createCookieYes(): .mode('self-hosted') requires either .backend(...) or .backendURL(...).`

Same — builder-only.

### `[cookieyes] initCookieYes() called more than once.`

Two modules call the builder, or it is inside a component body.

### `TS2353: ... does not exist in type 'CookieYesOfflineConfig'.`

You used a backend key (`apiUrl`, `apiKey`, `backend`) under `mode: "cookie-only"`. The union is discriminated on `mode` precisely to catch this. Switch mode or drop the key.

## Warnings

### `` [cookieyes] `regulation` is set manually, so region detection is ignored. ``

Both `regulation` and `region` are set. A manual regulation always wins. Remove `regulation` to let detection decide.

### `[cookieyes] mode: "offline" has been renamed to "cookie-only".`

A pure rename, identical behaviour. See [Migration](/docs/migration).

### `` [cookieyes] `builtInIntegrations` (formerly the `integrations` field) is deprecated ``

The `integrations` key changed meaning. See [Migration](/docs/migration) — this is the one deprecation that can change behaviour silently.

### `[cookieyes] A style was blocked by your Content-Security-Policy`

```text title="Console warning"
[cookieyes] A style was blocked by your Content-Security-Policy (style-src). CookieYes's own styling doesn't require "unsafe-inline" or a nonce, so this is likely unrelated to this SDK — check your own inline styles or third-party scripts.
```

A safety net, not an SDK error. The SDK's styling cannot violate `style-src`, so something else on the page did. See [CSP](/docs/styling/csp).

## Silent failures

The hardest category — no error, nothing in the console.

| Symptom | Cause | Fix |
| --- | --- | --- |
| Banner renders as unstyled text | Stylesheet not imported | `import "@cookieyes/react/styles.css"` |
| Preferences dialog unstyled, banner fine | Only `critical.css` loaded | Load `styles.css` too |
| Banner never appears | Already decided in this browser | Clear the cookie, or `reset()` |
| Nothing renders anywhere, no error at all | `initCookieYes()` never ran, or ran outside `"use client"` | Confirm the module is imported and starts with `"use client"` — see [the rule that breaks most first setups](/docs/getting-started/configuration#the-rule-that-breaks-most-first-setups) |
| Banner flashes and vanishes on every load | No `initialConsent` | Pass it via `CookieYesProvider` |
| Gated script never loads | Category not in the active taxonomy, or CSP blocked it | Check `useCategories().ids`, then `script-src` |
| Consent never reaches the backend | `cookie-only` mode, or no `apiUrl`/`backend`, or `connect-src` | POST is fire-and-forget — check the Network tab |
| Custom categories do not appear | Config rejected, fell back to the built-in five | Check the console for the validation warning |
| Tracker loads before the visitor saves | Gating on live values | Use `useConsentCategory()` |
| Dialog toggles never persist | No `Save`/`AcceptAll`/`RejectAll` rendered | Add one |
| Checkbox can be turned on but never off | `onChange={toggle}` passes an event | `onChange={(e) => toggle(e.target.checked)}` |
| CSS rule does nothing | Specificity tie, losing on source order | Import your sheet after `styles.css` |
| CSS rule needs `!important` | `theme` setting it inline | Remove the config key |
| Scoped/CSS-Modules styles never apply | Components portal into `<body>` | Use global CSS |
| Banner is English despite `locale: "fr"` | No `fr` entry in `i18n.messages` | Add the catalog |
| Focus jumps to page top on dialog close | Opened via the low-level runtime | Use `useConsentActions().showPreferences()` |
| Revoking consent does not stop a tracker | Injection is one-way within a page load | Mount `ReloadNotice`, or `reloadOnRevoke: true` |
| `strategy="lazyOnce"` changed nothing | Currently a no-op | Leave it unset |
| Reload notice never appears | Nothing declared itself reload-only | Register a `needsReload` handler |

## Every warning, word for word

Every message the SDK prints, quoted so that searching for any of it lands here. `${...}` marks a value filled in at runtime.

**Two things worth knowing before you read the list.** Only three of these are development-only — the rest **also print in production**, so a warning in a live console is a real signal. And several print **once per page load**, so a quiet console on your second attempt does not mean you fixed it; reload properly before concluding anything.

### Configuration and categories

| Message | What it means | Prints in production? |
| --- | --- | --- |
| `[cookieyes] Invalid categories config (${reason}). Falling back to the default five (necessary, functional, analytics, performance, advertisement).` | Your `categories` failed validation. The reason is in the parentheses | Yes |
| `[CookieYes] Received both \`regulation\` and the deprecated \`overrides.regulation\`. Using the top-level \`regulation\` and ignoring \`overrides\`.` | Drop the `overrides` object | Yes |
| `` [CookieYes] Received both `apiUrl` and the deprecated `backendURL`. Using `apiUrl` and ignoring `backendURL`. `` | Rename `backendURL` to `apiUrl` | Yes |
| `[cookieyes] mode: "offline" has been renamed to "cookie-only".` | A rename. Both behave identically | Yes — **once per page load** |
| `` [cookieyes] `builtInIntegrations` (formerly the `integrations` field) is deprecated `` | Move to `integrations` with a preset from `@cookieyes/scripts` | Yes — **once per page load** |
| `` [CookieYes] `createCookieYes()` (the builder) is deprecated. `` | Use `initCookieYes(config)` | Yes — **once per page load** |
| `[cookieyes] initCookieYes() called more than once. Replacing the previous runtime.` | Two `initCookieYes()` calls. Often React Strict Mode in development; otherwise a genuine double setup | Yes |

## Working as intended

These arrive as bug reports and are not bugs. Each is correct behaviour with a specific reason.

### The banner will not come back after I accepted

**Correct.** The banner shows until the visitor decides, then never again — that is the entire point. To test repeatedly, see [Reset and re-test](#reset-and-re-test).

### I cannot see my own banner

**Probably correct.** With region detection configured, the banner applies where the regulation applies. If you are testing from a region that maps to no regulation, you will not see it. Check `useRegion()` for what resolved and why, or set `regulation` manually while developing.

### The reload notice never appears

**Correct, if you tested by rejecting first.** The notice appears only when something that *was* running has been switched off. Reject on a first visit and nothing was ever running, so there is nothing to warn about. To see it: accept, reload, then withdraw.

### I withdrew consent and the embedded video is still there

**Correct.** A `GatedFrame` that has already loaded stays for the rest of that page visit; it is blocked on the next load. Withdrawing consent does not retroactively unload an iframe.

### I withdrew consent and the tracking script is still loaded

**Correct, and unavoidable.** You cannot un-run code that has already executed. The SDK stops or silences vendors that support it; the rest need a reload. This is the one case above with a compliance consequence — see [the full explanation](#i-withdrew-consent-and-the-tracking-carried-on).

### The banner is not where I put it in my code

**Correct.** The banner and recall button are moved to the very start of `<body>` so a keyboard visitor reaches them on the first Tab rather than after your entire navigation. See [Accessibility](/docs/accessibility#the-banner-and-recall-button-are-moved-to-the-top-of-the-page).

### All my returning visitors got asked again

**Correct, if you changed your category list.** Consent is recorded against a fingerprint of the categories in effect. Change the categories and previous answers no longer describe what you are asking, so everyone is re-asked. See [re-prompts](/docs/components/cookie-preferences#changing-categories-re-prompts-every-returning-visitor).

## Reset and re-test

### Clear a stored choice so the banner returns

```js title="DevTools console"
document.cookie = "cookieyes-consent=; max-age=0; path=/";
location.reload();
```

Or call `useConsentActions().reset()` from a dev-only control.

### See the banner when your own location would not trigger it

Set `regulation` explicitly while developing — `"GDPR"` gives you the opt-in banner — instead of relying on `region.detect`.

### Trigger the reload notice deliberately

It needs a specific sequence, because it only fires on a withdrawal:

1. **Accept** the category your reload-only tool is gated on.
2. **Reload** the page, so the tool actually starts.
3. **Withdraw** that category.

Rejecting on a first visit will never show it, and that is correct.

### Check these first

If nothing works at all, in this order:

1. Is `@cookieyes/react/styles.css` imported exactly once at your app root?
2. Does the module calling `initCookieYes()` start with `"use client"`, and is it imported on the path to your components?
3. Is there a `cookieyes-consent` cookie already recording a decision?
4. Is anything in the console? Several failures warn rather than throw.
5. Are `<CookiePreferences />` and — under CCPA — `<CookieOptOut />` actually mounted?

## Known bugs

Confirmed problems on our side. If you are seeing one of these, it is not a configuration mistake and there is no setting to find.

### The "Do Not Sell" dialog writes every category, not just the one it names

`OptOut.Save` calls `rejectAll()` when the box is ticked and `acceptAll()` when it is not — so a visitor who opens it, decides *not* to opt out, and saves has granted every category, overwriting earlier rejections. Its checkbox also derives its initial state from a hardcoded `analytics` category name, so a custom taxonomy without one always starts ticked, and it reads live rather than committed values.

Under review. Documented in full on [OptOut primitives](/docs/headless/opt-out#what-save-actually-writes) — do not build on the current semantics.

### A `Preferences.*` slot outside its Root fails silently

It should throw, and the guard for it exists in our source, but it is not wired to any slot. A `Preferences.*` component used outside `<Preferences.Root>` renders normally and quietly ignores every interaction instead of telling you why. `OptOut.*` does throw, but only from the four slots that read dialog state.

## Behaviour and trade-offs

### Hooks return defaults; `getCookieYes()` throws

Deliberate. A missing runtime should not crash a render, but module-level code that genuinely requires one should fail loudly. If you are getting defaults where you expected real state, the runtime is not registered — the hook is not hiding an error, it is telling you the same thing quietly.

### The consent POST is silent by design

Failures are caught and swallowed so a broken endpoint never breaks the consent flow or shows an error to a visitor. There is no retry and no response parsing. So a wrong `apiUrl`, a CORS failure, a CSP block, and a 500 all look identical from inside your app. Diagnose in the Network tab.

### A category validation failure falls back rather than throwing

An invalid `categories` config logs a warning and uses the built-in five. Common causes: no category marked `required: true`, or an id colliding with a reserved cookie meta key — `consentid`, `consent`, `action`, `tax`, `lastRenewedDate`.

### Reading the cookie directly

```text title="Raw cookie value"
consentid:abc123,consent:yes,action:yes,tax:1a2b3c,necessary:yes,analytics:no,lastRenewedDate:1735689600000
```

Comma-separated `key:value`. Five meta keys as above; every other pair is a category id mapped to `yes`/`no`. `tax` is the taxonomy signature — if it does not match your current config, the visitor is re-asked, which is correct.

### Testing consent-dependent code

Use `@cookieyes/test` rather than mocking. It runs core's real engine, so a passing test means the code actually works. `seedConsentCookie` sets up a returning visitor; `resetConsentTestState` clears between tests. A parity test asserts the harness cannot drift from production behaviour.

### First-paint problems need a real browser

jsdom has no paint, no layout shift, and does not resolve CSS custom properties, so unit tests cannot tell you whether a visitor actually *saw* the banner. Three manual checks:

1. Server-render with **JavaScript disabled** and reload. The banner must be fully styled — a transparent banner means the theme tokens were lost.
2. Throttle CPU to 20× and reload. The banner must not visibly disappear and fade back in.
3. Accept, then reload. The banner must be absent from View Source, not flash and vanish.

## Complete example

A diagnostic component for a dev environment:

```tsx title="components/ConsentDiagnostics.tsx"
"use client";

import {
  useCategories,
  useConsent,
  useConsentActions,
  useRegion,
  useReloadNotice,
} from "@cookieyes/react";

export function ConsentDiagnostics() {
  const { consentId, hasActed, categories, committedCategories } = useConsent();
  const { region, regulation, source, confidence } = useRegion();
  const { ids, requiredIds, isDefault } = useCategories();
  const { required, reasons } = useReloadNotice();
  const { reset, showPreferences } = useConsentActions();

  if (process.env.NODE_ENV === "production") return null;

  return (
    <pre style={{ fontSize: 12 }}>
      {JSON.stringify(
        {
          // "unregistered" here means initCookieYes() has not run.
          consentId: consentId || "unregistered",
          hasActed,
          regulation: `${regulation} (via ${source}, ${confidence})`,
          region: region ?? "unknown",
          taxonomy: { ids, required: [...requiredIds], isDefault },
          // If these disagree, someone has unsaved toggles open.
          live: categories,
          committed: committedCategories,
          reloadNeeded: required ? reasons : false,
        },
        null,
        2,
      )}
      <button type="button" onClick={() => showPreferences()}>
        Open preferences
      </button>
      <button type="button" onClick={() => reset()}>
        Reset consent
      </button>
    </pre>
  );
}
```

## Across the SDK

Error messages come from `@cookieyes/core` and `@cookieyes/react`, and are identical in `@cookieyes/nextjs` since it mirrors the `react` surface. `@cookieyes/core` throws none of the React-specific errors — no runtime registry, no primitives — so in core the equivalent failure is simply holding a runtime object you never created.

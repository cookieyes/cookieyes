## Scope of this page

This page covers **keyboard operability, focus management, screen-reader labelling, and reduced motion** across [`CookieBanner`](/docs/components/cookie-banner), [`CookiePreferences`](/docs/components/cookie-preferences), [`CookieOptOut`](/docs/components/cookie-opt-out), [`RecallButton`](/docs/components/recall-button) and [`ReloadNotice`](/docs/components/reload-notice).

<Callout type="warn">
  **This is not a blanket conformance claim.** It is not a statement that the SDK is "WCAG 2.1 AA compliant". It describes specific, verifiable behaviours and nothing beyond them.
</Callout>

**Outside this scope, and not covered:**

- **Colour contrast.** The defaults are a reasonable starting point, but the moment you set `theme.primaryColor` the ratio is yours. The brand colour does **not** change between light and dark schemes, so a colour that passes on white can fail on the dark surface. Only you can assess your own palette — see [Colour scheme](/docs/styling/color-scheme), which documents the dev-time contrast warning the SDK emits.
- **Text resizing and zoom**, which depend on your page's own layout and typography.
- **Anything in your own theme, content, or the surrounding page** — including whether rejecting consent is as easy as accepting it, which is a design decision you own and auditors check.

This page is written to be handed to an accessibility reviewer as-is.

## What you get by default

If you use the ready-made components unchanged, everything below is already handled:

```tsx title="app/cookieyes.tsx"
"use client";

import {
  CookieBanner,
  CookiePreferences,
  RecallButton,
  initCookieYes,
} from "@cookieyes/react";

initCookieYes({ mode: "cookie-only", regulation: "GDPR" });

export function CookieYesRoot() {
  return (
    <>
      <CookieBanner />
      <CookiePreferences />
      <RecallButton />
    </>
  );
}
```

The same behaviour holds when you build on [primitives](/docs/headless/overview), because it lives in the `Root` components rather than the styled markup. Building on hooks alone means implementing all of it yourself — see [If you build your own](#if-you-build-your-own).

## Keyboard behaviour

### Tab order, per component

Documented in order so a custom implementation can match it.

| Component | Tab order |
| --- | --- |
| **Banner** (GDPR) | Preferences → Reject All → Accept All → branding link |
| **Banner** (CCPA) | Close → Do Not Sell → branding link |
| **Preferences** | Close → each category toggle, in configured order → Reject All → Save → Accept All → branding link |
| **Opt-out** | Close → opt-out checkbox → Cancel → Confirm → branding link |
| **Recall button** | A single button |

Category toggles follow the configured taxonomy's declaration order, not alphabetical order. A category marked `required` renders as **plain text rather than a disabled control**, so it is not in the tab order at all.

<Callout type="warn">
  **On narrow viewports the banner's visual order differs from its tab order.** Below 440px the actions stack vertically and CSS `order` presents them as Accept All, Preferences, Reject All — while the DOM order, and therefore the keyboard tab order, stays Preferences → Reject All → Accept All.

  CSS `order` never changes focus sequence. If that divergence matters to your audit, override the `order` declarations on `.cy-banner-actions .cy-btn` so the two agree — see [Custom CSS](/docs/styling/custom-css).
</Callout>

### The banner deliberately does not trap focus

The banner carries `role="dialog"` with **`aria-modal="false"`**, and does not trap focus. Both pop-ups do the opposite: `aria-modal="true"` and a real focus trap.

That combination is unusual enough to be worth stating with its reasoning. A consent banner appears unbidden on arrival, so trapping focus in it would imprison a keyboard user in a prompt they did not ask for and could not leave without answering. But it still needs to be announced as a distinct region rather than as anonymous page content — hence the dialog role without the modality. **A keyboard user can Tab straight past the banner into your page.**

The two pop-ups are different: the visitor deliberately opened them, and they are genuinely modal, so holding focus is correct.

### Escape closes both pop-ups

`Escape` closes `CookiePreferences` and `CookieOptOut`. The listener is attached to the **document**, not to the dialog element, so it works regardless of where focus currently sits — including if focus has somehow escaped the dialog.

Escape does not dismiss the banner. There is no "dismiss without deciding" action under GDPR.

### Tab wraps inside a pop-up

While a pop-up is open, `Tab` from the last control moves to the first, and `Shift+Tab` from the first moves to the last. Focus cannot leave the dialog by keyboard.

<Callout type="warn">
  **Edge case if you build a custom pop-up with disabled buttons.** The trap collects focusable elements with the selector `button, [href], input, select, textarea, [tabindex]:not([tabindex="-1"])`. A **disabled** button matches `button` while not actually being focusable, so if a disabled control ends up first or last in your dialog, wrapping will try to focus something that cannot take focus.

  Nothing in the shipped components hits this — a required category renders as text rather than a disabled toggle, which is why. It is a latent edge for custom pop-ups only. Avoid putting a disabled control first or last, or give it `tabindex="-1"` explicitly.
</Callout>

A control that is focusable by other means — a `div` with a click handler and no `tabindex` — is not in the cycle either, and is not keyboard-operable to begin with. Use real elements.

## Focus management

This is the most intricate part of the implementation, and the reasoning matters as much as the behaviour, because the obvious implementation is wrong.

### Opening moves focus onto the pop-up itself

Not onto its first control — onto the dialog container, which carries the `aria-label`. That is what makes a screen reader announce *"Cookie preferences, dialog"* rather than falling back to page-level context.

For this to work the container must be **programmatically focusable without being a tab stop**: it carries `tabIndex={-1}`. If you build a custom pop-up and omit that, `.focus()` on the container silently does nothing and the announcement is lost.

### Closing returns focus to whatever opened it

Closing by saving, cancelling, or pressing `Escape` returns focus to the control that opened the pop-up.

### The opener is captured at the moment of the click

**Not when the pop-up mounts.** This is the part that is easy to get wrong.

Opening a pop-up also hides the banner, in the same render. So by the time a mount effect runs inside the dialog, the button that triggered the open may already be gone from the DOM — and the browser will have reset focus to `<body>`. An implementation that captures "the previously focused element" in the dialog's own effect therefore remembers `<body>`, and returns focus to the top of the page.

Capturing synchronously in the click handler, before that re-render happens, is the only reliable point.

### If the opener did not survive, we match it by label

The opener can legitimately unmount while its pop-up is open — the banner and the recall button both hide when a pop-up opens, and remount as **new DOM nodes** when it closes. A stale reference is simply disconnected, and calling `.focus()` on it does nothing at all.

So alongside the element reference we capture its rendered text or `aria-label`. On close, if the original node did not survive, we search for its replacement by that same label. "Do Not Sell" lands back on "Do Not Sell" — not on whichever control happens to be first.

### It works for your own triggers too

The capture lives in the shared opening action, not in our components. So [`useConsentActions().showPreferences()`](/docs/hooks/use-consent-actions) and `showOptOut()` record focus wherever they are called from — a footer link, a menu item, your own button — and focus return works with no `ref` and no restore logic of your own.

<Callout type="warn">
  Calling `runtime.manager.showPreferences()` directly through [`useConsentRuntime()`](/docs/hooks/low-level-hooks) **skips the capture entirely**, and focus falls back to the top of the page on close. Always use the action hook for anything a visitor triggers.
</Callout>

## What screen-reader users experience

### The banner announces itself, on a deliberate delay

When the banner appears, its title is announced through an `aria-live="assertive"` region — after a **700ms delay**, not on React's next tick.

The delay is deliberate. Immediately after a page loads, screen readers are typically still announcing the page itself, and a live-region update fired inside that window is commonly **dropped rather than queued**. Waiting until that has settled is what makes the announcement reliably heard.

### The announcement region is always in the page

The live region sits permanently in the document rather than appearing along with the banner. Updating an element assistive technology has been tracking all along is more reliable than inserting a new one and hoping it is noticed — which matters for a later appearance, after `reset()`, as much as for the first.

### Roles and labels, per component

| Component | Role | Accessible name |
| --- | --- | --- |
| Banner | `role="dialog"`, `aria-modal="false"` | The banner title |
| Preferences | `role="dialog"`, `aria-modal="true"` | `preferencesDialogLabel` |
| Opt-out | `role="dialog"`, `aria-modal="true"` | `optOutDialogLabel` |
| Opt-out confirmation | `role="status"` | Announced when the choice is recorded |
| Reload notice | `role="alert"` | Announced immediately |
| Category toggles | `role="switch"` + `aria-checked` | The category name |
| Category list | `role="list"` / `role="listitem"` | — |
| Recall button | Button | `recallButtonLabel` |
| Close buttons | Button | `bannerCloseLabel` / `preferencesCloseLabel` / `optOutCloseLabel` |

**Every one of these labels comes from the translation system**, so a German site announces its dialogs in German. Each close button renders only an `aria-hidden` icon, which means the label *is* the button's entire accessible name — there is nothing else for a screen reader to fall back on. See [Translations](/docs/translations).

### The banner and recall button are moved to the top of the page

Both render into a portal root inserted as the **first child of `<body>`** — inserted, not appended.

This is an accessibility mechanism, not an implementation detail: it means the banner is reachable within the **first Tab** rather than after every link in your navigation. Mount `<CookieYesRoot />` at the end of your layout, as the docs and CLI scaffold suggest, and it is still first in tab order.

It also renders inline on the server and relocates after mount, matching on the first client pass so hydration does not mismatch.

## Reduced motion

When a visitor has asked their device to reduce motion, **all entrance and exit animation is removed** — the banner's slide-in, the dialog overlay and dialog fade, the recall button's pop-in, and the reload notice.

**Everything still appears and works identically.** Nothing is hidden, delayed, or disabled; only the movement is removed. The end state is exactly the same.

If you replace our CSS, you own this. Preserve it with:

```css title="app/consent.css"
@media (prefers-reduced-motion: reduce) {
  [data-cy-part="banner"],
  [data-cy-part="dialog"] {
    animation: none;
    transition: none;
  }
}
```

See [Custom CSS](/docs/styling/custom-css) and the [part and state contract](/docs/styling/part-and-state-contract) for the selectors.

## What is tested, and what is not

### Automated

`axe-core` runs on every change and **fails the build** on any violation. Coverage is exactly:

| Test case | Component |
| --- | --- |
| Banner, GDPR mode | `CookieBanner` |
| Banner, CCPA mode | `CookieBanner` |
| Preferences dialog, open | `CookiePreferences` |
| Opt-out dialog, open | `CookieOptOut` |

Four cases, three components.

<Callout type="warn">
  **These run in a simulated browser (jsdom), which has no layout and no paint.** Colour contrast, visible text sizing, and anything else that depends on rendering **cannot be evaluated and is skipped**.

  In one sentence: it catches structural and labelling regressions — missing accessible names, wrong roles, broken labelling — **not the full accessibility surface. It is a safety net, not a substitute for testing by hand.**
</Callout>

**Reconciling scope with coverage**, so the two do not quietly disagree:

- **`RecallButton` is in the scope above but has no automated accessibility test.** Its labelling is covered by other tests, but axe does not run against it.
- **`ReloadNotice` is announced to screen readers** via `role="alert"` and is in the scope above, but likewise has no axe coverage.

Neither is necessarily a defect. Both are stated so that a reviewer reading the scope is not misled about what the automated suite actually proves.

### Manual

The keyboard and focus-management behaviour on this page was verified by hand across desktop, tablet and mobile viewports, in both light and dark colour schemes, with **VoiceOver**. If something does not behave as described with your screen reader, please open an issue — that is a bug worth hearing about.

## If you build your own

Everything above comes free with the ready-made components. Assembling your own from [primitives](/docs/headless/overview) keeps most of it, because the behaviour lives in the `Root` components. Building on hooks alone means you own all of it.

### What the primitives still give you

| Behaviour | Provided by |
| --- | --- |
| Focus trap, Escape, autofocus, focus restoration | [`Preferences.Root`](/docs/headless/preferences), [`OptOut.Root`](/docs/headless/opt-out) |
| First-child portal placement, the delayed announcement | [`Banner.Root`](/docs/headless/banner) |
| Switch semantics on toggles | `Preferences.Category` |
| Focus capture on open | [`useConsentActions()`](/docs/hooks/use-consent-actions) |
| Reduced-motion handling | The SDK stylesheet, if you keep it |

### Checklist for a custom interface

Whatever you replace, preserve these:

- [ ] **Pop-ups hold focus** — Tab and Shift+Tab wrap inside; focus cannot escape. → [`Preferences.Root`](/docs/headless/preferences)
- [ ] **Escape closes both pop-ups**, listening at document level. → [`Preferences.Root`](/docs/headless/preferences)
- [ ] **Focus returns to the opener on close**, including when the opener has remounted. → [`useConsentActions()`](/docs/hooks/use-consent-actions)
- [ ] **Every control has a visible keyboard outline** — a real `:focus-visible` style, not the browser default you may have reset away.
- [ ] **Reduced motion is honoured** — no entrance or exit movement, same end state. → [Custom CSS](/docs/styling/custom-css)
- [ ] **The banner is reachable in the first Tab**, not after your navigation. → [`Banner.Root`](/docs/headless/banner)
- [ ] **Dialog containers carry `tabIndex={-1}`** so they can receive focus without becoming a tab stop.

<Callout type="warn">
  **The automated coverage above applies to the ready-made components only.** A custom interface is not covered by it and needs its own accessibility testing.
</Callout>

### The two easiest things to lose

Both are invisible to sighted testing, which is exactly why they get dropped:

1. **The banner's delayed announcement.** A naive `aria-live` region placed inside a conditionally mounted banner, updated on mount, is announced during the page-load window — and is commonly dropped. Replicate both the delay and the outside-the-mount-cycle placement, or keep `Banner.Root`.
2. **Label-matching focus return.** Restoring focus with a plain saved reference works until the opener unmounts, which the banner and recall button both do whenever a pop-up opens. Then the reference is disconnected, `.focus()` silently does nothing, and the visitor is dropped at the top of the page.

## Common mistakes

**Focus jumps to the top of the page when a pop-up closes.**
Opened via `runtime.manager.showPreferences()` instead of `useConsentActions().showPreferences()`, so no opener was captured.

**Tab from the address bar reaches every nav link before the banner.**
A custom banner without `Banner.Root`, so it lost the first-child portal placement.

**A screen reader never announces the banner on first load.**
A custom `aria-live` region inside the conditionally mounted banner, fired during the page-load window. Keep `Banner.Root`, or replicate the delay and the placement.

**Focus escapes a custom pop-up.**
Controls outside the trap's selector list — usually a `div` with a click handler. Use real interactive elements.

**Tab wrapping lands on nothing in a custom pop-up.**
A disabled button first or last in the dialog. It matches the focusable selector without being focusable.

**A screen reader announces the dialogs in English on a translated site.**
This was true of nine strings in earlier versions and is fixed — all accessible names now come from the translation system. Check the language actually supplies them; a missing key falls back to English.

**An audit flags the banner as invalid consent.**
Reject is visually subordinate to accept, or there is no explicit reject. A design issue rather than an SDK one, and yours to fix.

**Contrast fails in dark mode only.**
`theme.primaryColor` does not change between schemes. Override it per scheme — see [Colour scheme](/docs/styling/color-scheme).

## Across the SDK

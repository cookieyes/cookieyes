## When to use it

Use this to build your own consent controls: a footer "Cookie settings" link, a custom banner's buttons, a "reset consent" button in a dev panel.

You do not need it with the styled components or the primitives — [`Banner.AcceptAll`](/docs/headless/banner) and friends already call these actions. Reach for the hook when you are building a trigger the SDK does not provide.

To *read* consent, pair this with [`useConsent()`](/docs/hooks/use-consent). Reading and writing are deliberately two separate hooks: this one only writes, never subscribes, and so never causes a re-render — see [Reading and writing are two hooks, not one](/docs/hooks/use-consent#reading-and-writing-are-two-hooks-not-one) for why, and for a mapping if you are arriving from a library with a single combined hook.

## Basic usage

The three things people most often build with this hook are a custom accept button, a preferences interface with per-category toggles, and a way to withdraw a decision.

**A custom accept button.** `acceptAll()` grants every category and commits in one call — there is no separate save step:

```tsx title="components/AcceptButton.tsx"
"use client";

import { useConsentActions } from "@cookieyes/react";

export function AcceptButton() {
  const { acceptAll } = useConsentActions();

  return (
    <button type="button" className="btn-primary" onClick={acceptAll}>
      Accept all cookies
    </button>
  );
}
```

**A "reset my choices" control.** `reset()` clears the recorded decision entirely, so the banner returns as it would for a first-time visitor:

```tsx title="components/ResetChoices.tsx"
"use client";

import { useConsentActions } from "@cookieyes/react";

export function ResetChoices() {
  const { reset } = useConsentActions();

  return (
    <button type="button" onClick={reset}>
      Reset my cookie choices
    </button>
  );
}
```

**A link that reopens the preferences dialog** — the usual footer control:

```tsx title="components/CookieSettingsLink.tsx"
"use client";

import { useConsentActions } from "@cookieyes/react";

export function CookieSettingsLink() {
  const { showPreferences } = useConsentActions();

  return (
    <button type="button" className="footer-link" onClick={() => showPreferences()}>
      Cookie settings
    </button>
  );
}
```

For the third case — a full preferences interface with a toggle per category — see [Complete example](#complete-example) below, which wires `updateCategory` and `save` together.

## Options

`useConsentActions()` takes **no arguments** and returns `ConsentActions`:

| Action | Signature | Commits? | Description |
| --- | --- | --- | --- |
| `acceptAll` | `() => void` | Yes | Grants every category and saves |
| `rejectAll` | `() => void` | Yes | Denies every non-required category and saves |
| `acceptSelected` | `(categories: ConsentCategory[]) => void` | Yes | Grants exactly this list, denies the rest, saves |
| `save` | `() => void` | Yes | Commits the current live values |
| `updateCategory` | `(category: ConsentCategory, value: boolean) => void` | **No** | Sets a live value only |
| `reset` | `() => void` | Yes | Clears the decision — the banner shows again |
| `showPreferences` | `() => void` | — | Opens the preferences dialog |
| `hidePreferences` | `() => void` | — | Closes it |
| `showOptOut` | `() => void` | — | Opens the CCPA opt-out dialog |
| `hideOptOut` | `() => void` | — | Closes it |

## Behaviour and trade-offs

### `updateCategory` does not save

It writes the **live** value — the same thing a dialog toggle does. Nothing is committed until `save()`. A custom dialog therefore needs `updateCategory` for each toggle *and* a `save()` on its confirm button. Call only `updateCategory` and the visitor's choices silently evaporate.

For a one-shot write that commits immediately, use `acceptSelected([...])` instead.

### `acceptSelected` is exhaustive

It grants the ids you pass and **denies everything else**. It is not additive. To grant analytics while keeping existing choices, read the current committed state, merge, and pass the full list:

```tsx title="components/GrantAnalytics.tsx"
"use client";

import { useConsent, useConsentActions } from "@cookieyes/react";

export function GrantAnalytics() {
  const { committedCategories } = useConsent();
  const { acceptSelected } = useConsentActions();

  function grantAnalytics() {
    const granted = Object.entries(committedCategories)
      .filter(([, isGranted]) => isGranted)
      .map(([id]) => id);

    acceptSelected([...new Set([...granted, "analytics"])]);
  }

  return (
    <button type="button" onClick={grantAnalytics}>
      Enable analytics
    </button>
  );
}
```

### `showPreferences` and `showOptOut` remember focus

Both record which element had focus at the moment they were called, and that is what lets focus return to it when the dialog closes. **This works from your own trigger, not just the built-in ones** — a footer link, a menu item, a button inside a settings page all get correct focus return for free, with no `ref` and no restore logic of your own.

The capture happens synchronously inside your click handler, which is the only reliable point: opening a dialog also hides the banner in the same render, so by the time an effect could run, the element that triggered the open may already have been removed from the DOM.

Calling `runtime.manager.showPreferences()` directly through [`useConsentRuntime()`](/docs/hooks/low-level-hooks) skips the capture entirely — focus falls back to the top of the page on close. Use this hook for anything a visitor triggers.

### `reset` is a genuine reset

It clears the recorded decision entirely, so the banner reappears as if for a first-time visitor. Useful in a dev panel and for a "withdraw all consent" control. It does not unload anything already running — see [ReloadNotice](/docs/components/reload-notice).

### The actions are stable, and no-ops before mount

The returned object is memoised on the runtime, so it is safe in a `useEffect` dependency array. Before `initCookieYes()` has registered a runtime — during SSR, for instance — every action is a silent no-op rather than a throw, so a server-rendered button will not crash the render.

## Complete example

A complete custom banner built on the two hooks:

```tsx title="components/CustomBanner.tsx"
"use client";

import { useCategories, useConsent, useConsentActions } from "@cookieyes/react";

export function CustomBanner() {
  const { hasActed, categories } = useConsent();
  const { acceptAll, rejectAll, updateCategory, save } = useConsentActions();
  const { list, requiredIds } = useCategories();

  if (hasActed) return null;

  return (
    <div role="dialog" aria-label="Cookie consent" className="banner">
      <h2>We use cookies</h2>

      {list.map((cat) => {
        const required = requiredIds.has(cat.id);
        return (
          <label key={cat.id}>
            <input
              type="checkbox"
              checked={required || categories[cat.id] === true}
              disabled={required}
              onChange={(e) => updateCategory(cat.id, e.target.checked)}
            />
            {cat.label ?? cat.id}
          </label>
        );
      })}

      <div className="actions">
        <button type="button" onClick={rejectAll}>
          Reject all
        </button>
        <button type="button" onClick={acceptAll}>
          Accept all
        </button>
        {/* Without this, every toggle above is discarded. */}
        <button type="button" onClick={save}>
          Save my choices
        </button>
      </div>
    </div>
  );
}
```

<Callout type="warn">
  This example reimplements markup, focus handling, and ARIA that [`Banner` primitives](/docs/headless/banner) provide for free. Prefer the primitives unless you genuinely need something they cannot express.
</Callout>

## Common mistakes

**Toggles work in the UI but nothing persists.**
`updateCategory` without `save()`. Add a save action.

**Granting one category silently revoked the others.**
`acceptSelected` is exhaustive. Merge with the current committed state first.

**Focus jumps to the top of the page when a dialog closes.**
You opened it via the low-level runtime instead of `showPreferences()`, so no focus was remembered.

**`showPreferences()` does nothing.**
[`CookiePreferences`](/docs/components/cookie-preferences) or your own `Preferences.Root` is not mounted. The action only sets state.

**Buttons do nothing and there is no error.**
No runtime is registered yet, so the actions are no-ops. Check that `initCookieYes()` runs in a `"use client"` module.

**The banner will not come back for testing.**
Call `reset()`, or clear the `cookieyes-consent` cookie.

## Across the SDK

Identical in `@cookieyes/react` and `@cookieyes/nextjs`.

Eight of the ten actions are a thin wrapper over `consentManager`, so `@cookieyes/core` has a direct equivalent for each. **Two of the names differ from the operation they call** — worth knowing if you are reading a stack trace, where you will see the right-hand name, not the one you called:

| Action | Calls |
| --- | --- |
| `acceptAll` | `consentManager.acceptAll()` |
| `rejectAll` | `consentManager.rejectAll()` |
| `acceptSelected` | `consentManager.acceptSelected()` |
| `updateCategory` | `consentManager.updateCategory()` |
| **`save`** | **`consentManager.savePreferences()`** |
| **`reset`** | **`consentManager.resetConsent()`** |
| `showPreferences` | `consentManager.showPreferences()` |
| `hidePreferences` | `consentManager.hidePreferences()` |

The remaining two are **not** on `consentManager` at all. `showOptOut` and `hideOptOut` call `showOptOut()` / `hideOptOut()` on the React runtime itself, because the CCPA opt-out dialog's open state is a React-layer concept — `@cookieyes/core` has no such methods, and `ConsentManager` has no opt-out members. In a stack trace they surface under the runtime, not the manager. If you are building a CCPA opt-out control against `@cookieyes/core` directly, you are responsible for that dialog's open state yourself.
